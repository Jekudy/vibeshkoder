- (direction) Использовать Coaching path; результат нужен как машинный контракт и короткий человекочитаемый walkthrough для RFC #484.
- (event) Инцидент @predko подтверждён: старые значения Лондон и От участника чата были перенесены из прежней строки Google Sheet в новую application планировщиком pull-sync.
- (capability) CAP-1: пользователь видит единый смысл поля и своё значение одинаково в вопросах, preview, кандидатской анкете, финальном или обновлённом интро и экспорте; успех — все поверхности получают подписи и порядок из одного контракта полей.
- (capability) CAP-2: подтверждение фиксирует неизменяемую версию пользовательского блока; успех — preview, поручительство, вступление и публикация используют одну и ту же подтверждённую версию без повторной сборки из изменяемых текущих ответов.
- (capability) CAP-3: существующий участник может переписать себя без потери действующего интро; успех — старая версия остаётся текущей до успешной публикации нового сообщения Обновлённое интро, после чего новая версия становится текущей.
- (capability) CAP-4: общий источник знакомства можно уточнить конкретным Telegram-ником при переписи; успех — значение без конкретного @username запрашивается заново, а уже конкретный @username переносится без повторного вопроса.
- (capability) CAP-5: Google Sheet отражает текущую подтверждённую версию, но не меняет её; успех — редактирование или устаревшая строка Sheet не меняет ответы, preview, intro или сообщения Telegram.
- (capability) CAP-6: повторные confirm, join и задачи публикации безопасны; успех — одна подтверждённая версия порождает не более одного сообщения каждого типа и не смешивается с другой application.
- (decision) При переписи публиковать новое сообщение Обновлённое интро, а не редактировать или удалять прежнее; история чата сохраняется.
- (decision) История источника знакомства допускает обычный переход только от общего значения к конкретному @username; замена одного конкретного ника другим не входит в обычную перепись.
- (constraint) PostgreSQL хранит канонические ответы и версии; Telegram и Google Sheet являются представлениями, а Sheet никогда не пишет в questionnaire_answers или intros.
- (constraint) Старое интро остаётся действующим при незавершённой переписи, ошибке подтверждения или ошибке публикации; частичный draft не может стать текущим.
- (constraint) Пользовательский блок подтверждённой версии не меняется из-за деплоя, новой формулировки вопросов, поручительства, задержки до вступления или Sheet-sync.
- (constraint) Решение встраивается в существующие Application, QuestionnaireAnswer и Intro и не добавляет новый сервис или зависимость без необходимости.
- (decision) Форматная нормализация допустима только до preview и видна пользователю; после подтверждения значение версии неизменно.
- (note) Non-goals: редактор отдельных полей, редактирование анкет из Sheet, удаление старых сообщений, ретроактивное угадывание legacy-ответов и transactional outbox без доказанной необходимости.
- (event) Spec intent collected from user decisions, production evidence, current code and RFC #484.
- (event) Self-validate pass 1 coherence: PASS — six capabilities have intent and testable success, constraints bend design, non-goals bound scope, and the success signal is demonstrable.
- (event) Self-validate pass 2 preservation: PASS — incident lineage, uniform field contract, immutable confirmation, new-message refresh, conditional referral refinement, Sheet precedence, failure safety and version-bound actions all landed.
- (note) Wrapper-only content omitted from the contract: coaching mechanics, worktree setup and conversational acknowledgements.
- (event) Spec finalized for architecture review.
- (decision) Supersedes prior non-goal: delivery reliability must follow inherited ADR-0018; whether implemented as outbox is an architecture concern, not excluded by the product contract.
- (constraint) У пользователя может быть не более одной активной refresh-application; повторный /refresh возобновляет её, а не создаёт конкурирующую версию.
- (decision) CAP-6 confirmation binds application_id plus digest of the exact preview; confirmation is rejected if the draft changed after preview.
- (decision) Outbound Telegram and Sheet delivery follows inherited ADR-0018 via a durable Postgres outbox; the product contract requires recoverable delivery without making Sheet canonical.
- (constraint) Application fixes catalog_version at creation so prompts, required fields, public labels and preview remain one schema through completion.
- (constraint) Confirmed snapshot is the exact UTF-8 HTML user block shown in preview and later reused byte-for-byte; user answers are HTML-escaped before it is stored.
- (decision) Legacy Intro without application link remains valid until rewrite; the rewrite asks all fields and creates the first linked version rather than guessing from Sheet or old text.
