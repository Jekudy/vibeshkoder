- (direction) Пользователь выбрал новое сообщение Обновлённое интро для каждой успешной переписи; старые сообщения не редактируются и не удаляются.
- (direction) Источник знакомства уточняется при переписи только когда нет конкретного Telegram-ника; конкретный ник переносится в новую версию.
- (decision) AD-1 [ADOPTED]: парадигма Versioned Aggregate with Unidirectional Projections; Application и принадлежащие ей QuestionnaireAnswer образуют одну версию, а Telegram и Sheet только отображают подтверждённую версию. Binds CAP-1..CAP-6; prevents split-brain и смешивание ответов разных application.
- (decision) AD-2: один канонический каталог полей задаёт стабильный field_id, prompt, public_label, порядок, нормализацию и sheet_header. Binds CAP-1, CAP-4; prevents independent drift between questions, preview, chat and Sheet.
- (decision) AD-3 [ADOPTED]: PostgreSQL — единственный источник истины; Sheet-sync только пишет подтверждённое текущее состояние из БД и никогда не меняет QuestionnaireAnswer или Intro. Binds CAP-2, CAP-5; prevents rollback from stale Sheet rows.
- (decision) AD-4: confirmation freezes an application-scoped snapshot; candidate card, vouch, join intro and refresh publication render from that snapshot, never from answers selected by user_id plus is_current. Binds CAP-2, CAP-6; prevents template drift and cross-application mixing.
- (decision) AD-5: refresh uses publish-before-promote — previous Intro remains current while a new draft or confirmed unpublished version exists; after Telegram accepts a new Обновлённое интро, Intro atomically points to that application and Sheet is projected later. Binds CAP-3, CAP-5; prevents losing the current intro on abandonment or publish failure.
- (decision) AD-6: each downstream action carries application_id and records the Telegram message identity after success; callbacks reject stale application IDs, and recorded successful actions are idempotent. Binds CAP-2, CAP-6; prevents a vouch or retry applying to another revision and ordinary duplicate posts.
- (decision) AD-7: referral is profile-admission provenance with monotonic refinement general-to-concrete; refresh conditionally asks it only when no concrete @username exists. Binds CAP-4; prevents overwriting known provenance through ordinary profile rewriting.
- (constraint) Reuse the existing Python 3.12, aiogram, SQLAlchemy, PostgreSQL, Application, QuestionnaireAnswer and Intro boundaries; no new service or dependency.
- (constraint) Existing project deployment, authentication, privacy and environment invariants remain inherited; this feature spine does not redesign them.
- (assumption) Exactly-once delivery across an unknown Telegram network outcome is not guaranteed by Bot API; the initial implementation prevents duplicates after recorded success and surfaces the rare ambiguous crash window for reconciliation.
- (question) If a concrete referral @username is factually wrong, correction is outside ordinary refresh and needs a separate operator policy before implementation.
- (event) Architecture decisions collected for RFC #484; ready for distillation and reviewer gate.
- (constraint) Inherited ADR-0018 binds this feature: DB mutation plus Telegram or Sheet side effect uses a Postgres outbox row and APScheduler worker; no external broker.
- (decision) Supersedes the assumption that publication outbox is deferred: AD-5 must enqueue a version-bound intro publication transactionally and promote Intro only after the worker records Telegram success.
- (decision) AD-3 amended: confirmation atomically validates one answer per required field, checks application_id plus preview digest, persists confirmed_intro_text, moves status filling to confirmed and enqueues the first effect.
- (decision) AD-5 amended: intro_effect_outbox with unique application_id plus effect_kind is the durable record for candidate, final, refresh and Sheet effects; worker uses a committed processing claim before IO.
- (decision) AD-6 amended: publication identity is application_id plus effect_kind plus chat_id plus message_id; success transaction records identity and conditionally promotes current Intro.
- (decision) AD-8: Application persists flow_kind admission or refresh and base_application_id; a partial unique constraint permits one active refresh per user, and /refresh resumes it. Prevents parallel refresh versions racing.
- (decision) AD-9: Telegram intro success promotes Intro and enqueues Sheet projection in one transaction; Sheet worker skips an application that is no longer current. Prevents stale export and projection-before-publication.
- (constraint) QuestionnaireAnswer enforces one row per application_id plus stable field_id; question_index remains display order only.
- (constraint) Intro.intro_text is a compatibility projection of Application.confirmed_intro_text, never an independently writable canonical copy.
- (constraint) Root SPEC section declaring Sheet source of truth describes current legacy behavior and is superseded for RFC #484 by CAP-5 and AD-4; update root SPEC in the implementation PR when behavior changes.
- (decision) Ambiguous Telegram outcome moves effect to unknown and blocks blind resend; operator reconciliation resolves it because Bot API cannot prove whether a timed-out send was accepted.
- (decision) AD-2 amended: Application.catalog_version selects an immutable field catalog; intro-v2 is retained while any filling application references it.
- (decision) AD-3 amended: snapshot_html is exact HTML body built in catalog order with LF separators and escaped values; preview_digest is unpadded base64url of first 16 bytes of SHA-256 over UTF-8 snapshot_html.
- (decision) AD-5 amended: outbox stores attempt_count, attempt_started_at and last_error; a reaper moves expired processing to unknown and never blindly retries it.
- (decision) AD-9 amended: one APScheduler intro-effect worker with max_instances 1 processes effects sequentially; Sheet stale check and write cannot race another intro promotion in the supported single-replica runtime.
- (decision) AD-10: Intro.application_id migration is nullable; legacy rows remain unlinked and are not guessed. Member without linked Intro starts refresh with nullable base and header determined by whether Intro exists; first successful publication creates or links Intro.
- (constraint) System and user message fragments use explicit parse_mode HTML; snapshot_html is stored after escaping user values and is never escaped or formatted again.
- (constraint) Stale processing recovery requires an APScheduler reaper; operator resolves unknown by finding the Telegram post and recording its identity, or proving absence and resetting to pending.
