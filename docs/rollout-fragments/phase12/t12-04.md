# T12-04 Rollout Fragment

## Summary

Lands `ButlerService` — the orchestrator-only state machine for butler actions
per `PHASE12_PLAN.md` §5.D / §5.E: five transition methods (`plan_action`,
`confirm_action`, `execute_action`, `cancel_action`, `expire_action`), full
exception hierarchy (`ButlerActionError` + 5 subclasses), MSK-aligned rate
buckets, cross-user consent enforcement, evidence revalidation on all-confirmed,
and cascade-vs-callback race guard via `SELECT FOR UPDATE` coordination.
Foundation for T12-05 (Telegram handlers) and T12-06 (tool wrappers).

## Hard Constraints Honored

- **#1 NO LLM outside gateway** — `plan_action` delegates to `llm_gateway.plan_butler_action`; no direct anthropic/openai imports.
- **#2 NO raw DB outside repos** — all DB access via `ButlerActionRepo`, `ButlerActionConfirmationRepo`, `ButlerToolInvocationRepo`, `ButlerRateBucketRepo`; no raw SQL in butler.py.
- **#5 cross-user consent unbypassable** — `plan_action` creates individual confirmation rows for all `affected_user_ids`; `confirm_action` checks all rows before advancing to `pending_execution`.
- **#9 NULL ledger only for rejected/expired/cancelled** — `plan_action` writes `llm_usage_ledger_id` from gateway's ledger FK on every non-rejected path; Constraint #9 honored.

## Cross-Stream Contracts

- **T12-05** (Telegram handlers) consumes `plan_action`, `confirm_action`, `cancel_action`, `execute_action`, `expire_action` — requires `get_for_update()` on `ButlerActionRepo`, `get_for_action_user()` + `list_for_action()` + `mark_all_for_action()` on `ButlerActionConfirmationRepo`, and `update_invocation()` on `ButlerToolInvocationRepo` (noted as deferred repo additions).
- **T12-06** implements 5 `ButlerTool` classes; `execute_action` accepts `tool_registry` dict for injection.
- **T12-08** replay uses `evidence_context_hash` captured at plan time; `confirm_action` revalidates hash before moving to `pending_execution`.
