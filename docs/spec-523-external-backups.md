# SPEC — SHK #523: регулярные внешние бэкапы Shkoder и Harry в B2

Статус: черновик под реализацию. Дата: 2026-09-18. Тред: `thr_u72ausqdic`, родитель `thr_5r57pyq4zn`.
Issue: [#523](https://github.com/Jekudy/vibeshkoder/issues/523).

## Задача

Shkoder ежедневно дампится host-cron'ом, но копия остаётся на том же диске, что и база: потеря VPS
уничтожает и данные, и резерв. У Harry регулярного резервирования нет вообще — ни Postgres
(`harry-honcho-db`), ни постоянного состояния в volume `harry-hermes-data`. Надо довести обе системы
до состояния «копия лежит вне VPS, зашифрована, восстановление проверено на практике», переиспользуя
механизм, который уже работает у Foodzy (`rclone` → Backblaze B2), и не трогая сам Foodzy.

## Принятые решения

Все шесть — **решение оркестратора от 2026-09-17, ожидает подтверждения пользователем утром**.
Пользователь был недоступен; оркестратор ответил за него в треде `thr_5r57pyq4zn`.

| № | Решение | Значение |
|---|---|---|
| 1 | Хранилище | новый бакет `b2:vibe-backups`, префиксы `shkoder/` и `harry/` |
| 2 | Retention в B2 | 30 дней. Локальный retention Shkoder (7 дней) не меняется |
| 3 | Шифрование | `age`, асимметрично. Приватный ключ генерируется на маке, на VPS уходит только публичный |
| 4 | Состав Harry | Postgres + выборочное состояние без кэшей; SQLite снимается через `sqlite3 .backup` |
| 5 | Расписание | cron Shkoder 03:17 UTC не двигаем; заливка Shkoder 03:50 UTC, Harry 03:40 UTC |
| 6 | Доставка | скрипт в репозитории, установка на VPS вручную, процедура в runbook. `ops/compose/deploy.py` не трогаем |

Отдельно снято оркестратором: **оповещение о провале входит в скоуп** и не считается мониторингом.
Канал — тот же, что уже работает у Foodzy (Telegram через dev-бота), новых каналов не заводим.

## Инварианты

Первые семь — из файла инвариантов треда, дальше специфика этой реализации.

1. Существующие дампы, volumes и боевые данные только читаются. Ничего не удаляется и не
   перезаписывается. Существующий `/usr/local/sbin/shkoder-pg-backup.sh` и его cron не изменяются.
2. Бэкап не мешает работе сервисов: контейнеры не останавливаются, долгих блокировок БД нет
   (`pg_dump` работает под MVCC-снимком).
3. Секреты не попадают в репозиторий, в логи, в вывод команд и в текст issue. В коде — только имена
   переменных окружения. Приватный ключ `age` не печатается никуда и никогда.
4. Скрипт идемпотентен: повторный запуск не плодит дубли расписания (cron — один файл, перезапись
   целиком) и не ломает предыдущие копии.
5. Восстановление проверяется в изолированном контейнере, никогда не поверх боевой базы.
6. Падение бэкапа не молчит: ненулевой код возврата, запись в лог, Telegram-уведомление.
   `|| true` поверх ошибок запрещён.
7. **Retention удаляет только объекты, созданные этим же механизмом.** Удаление всегда ограничено
   и своим префиксом (`b2:vibe-backups/<service>/`), и `--include` по собственному шаблону имени.
   Удаление в корне бакета запрещено. Это прямой урок из находки: foodzy-скрипт выполняет
   `rclone delete --min-age 30d b2:foodzy-backups/` рекурсивно по всему бакету без фильтра имени —
   любой чужой объект там попадает под его политику. Наш механизм так делать не имеет права,
   и это покрыто тестом.
8. **Приватный ключ `age` никогда не попадает на VPS** — ни в файл, ни в переменную окружения,
   ни в аргумент команды. На VPS живёт только recipient (публичная часть).
9. **SQLite копируется только через `sqlite3 ".backup"`.** Копия, снятая `cp` при живом WAL, рваная:
   часть транзакций остаётся в `-wal`, и восстановленная база может оказаться в несогласованном
   состоянии. Процессы Harry пишут в эти файлы непрерывно, останавливать их нельзя (инвариант 2).
10. Заливается только проверенный артефакт: размер выше порога, а для Shkoder — ещё и возраст
    исходного дампа не старше 24 часов. Протухший дамп молча не заливается.

## Архитектура

### Что откуда берётся

**Shkoder.** Свой `pg_dump` не делаем — он уже есть и работает (лестница Ponytail, рунга
«уже есть в проекте»). Берём самый свежий `/data/coolify/backups/shkoder-postgres/shkoder-pg-*.dump`,
проверяем возраст и размер, шифруем, заливаем. Дубль дампа стоил бы лишних 50 МБ диска и второй
нагрузки на боевую БД.

**Harry.**
- `docker exec harry-honcho-db pg_dump -U postgres -d postgres --format=custom --no-owner --no-privileges`
- SQLite через `sqlite3 <src> ".backup <dst>"`: `state.db` (11 МБ), `kanban.db`, `cron/executions.db`
- файлы как есть: `auth.json`, `.env`, `channel_directory.json`, `mcp_sessions/`, `/srv/harry/config/`
- **исключены**: `cache/`, `audio_cache/`, `.cache/`, `.codex/`, `home/` — восстанавливаются сами,
  это 500 из 525 МБ volume'а
- `harry-honcho-redis` не бэкапим: это очередь deriver'а, состояние эфемерное

### Имена объектов

- `b2:vibe-backups/shkoder/shkoder-pg-<UTC-ts>.dump.age` — timestamp берётся из имени исходного дампа
- `b2:vibe-backups/harry/harry-<UTC-ts>.tar.gz.age`

### Пиковое потребление диска

Свободно 9.7 ГБ при 80% занятости — считаем до написания скрипта.

| Что | Пик | Живёт |
|---|---|---|
| Shkoder: временный `.age` | ~50 МБ | минуты, удаляется в `trap EXIT` |
| Harry: `pg_dump` honcho | ≤ 13 МБ (база 13 МБ, оценка до первого прогона) | минуты |
| Harry: снимки SQLite + файлы | ~11.5 МБ | минуты |
| Harry: `tar.gz` + `.age` | ~2 × 15 МБ | минуты |
| **Суммарный пик обоих** | **< 110 МБ** | |

Существующие локальные дампы Shkoder (7 × 50 МБ = 350 МБ) уже на диске и не растут — retention
не меняется. Промежуточные копии не накапливаются: временный каталог создаётся `mktemp -d` в
`/var/tmp` и удаляется в `trap EXIT` независимо от исхода.

### Секреты на VPS

`/srv/secrets/backup.env`, режим `0600`, владелец root. Содержит имена:
`AGE_RECIPIENT`, `TELEGRAM_DEV_BOT_TOKEN`, `ADMIN_TELEGRAM_ID`. Значения токена и chat_id — те же,
что уже работают у Foodzy; файл свой, чтобы не связываться с `/opt/foodzy/.env.prod` и не расширять
blast radius на чужой сервис.

### Файлы

| Путь | Назначение |
|---|---|
| `ops/vps/backup-to-b2.sh` | скрипт, один на оба сервиса, аргумент `shkoder\|harry` |
| `ops/vps/backup-to-b2.test.sh` | runnable-проверка логики без обращения к сети и диску |
| `ops/vps/vibe-b2-backup.cron` | содержимое `/etc/cron.d/vibe-b2-backup` |
| `docs/ops/external-backup-runbook.md` | установка, проверка, восстановление, ротация ключа |
| `docs/spec-523-external-backups.md` | этот файл |

На VPS скрипт ставится в `/usr/local/sbin/backup-to-b2.sh`, режим `0750`, владелец `root:root`.
Лог — `/var/log/vibe-b2-backup.log`.

### Коды возврата

`0` успех · `1` ошибка конфигурации (нет env-файла, нет обязательной переменной) · `2` источник
непригоден (дамп отсутствует, протух, слишком мал) · `3` ошибка шифрования · `4` ошибка заливки
или retention.

## Как проверяем

```bash
# тест логики (локально, без сети)
bash ops/vps/backup-to-b2.test.sh

# расписание на VPS
ssh foodzy-vps 'cat /etc/cron.d/vibe-b2-backup'

# объекты в B2 с датой и размером
ssh foodzy-vps 'sudo -n rclone lsl b2:vibe-backups/shkoder/ b2:vibe-backups/harry/'

# ручной прогон
ssh foodzy-vps 'sudo -n /usr/local/sbin/backup-to-b2.sh shkoder; echo exit=$?'
ssh foodzy-vps 'sudo -n tail -30 /var/log/vibe-b2-backup.log'

# негативный путь: несуществующий бакет
ssh foodzy-vps 'sudo -n env B2_BUCKET=vibe-backups-does-not-exist /usr/local/sbin/backup-to-b2.sh shkoder; echo exit=$?'
```

### Прогон восстановления (DoD 5)

Выполняется **на маке**, не на VPS: приватный ключ `age` живёт только там (инвариант 8), а
изолированный контейнер поверх локального Docker гарантированно не касается боевой базы.

1. `ssh foodzy-vps 'sudo -n rclone cat b2:vibe-backups/shkoder/<объект>' > /tmp/restore.dump.age`
2. sha256 сверяется с тем, что скрипт записал в лог при заливке
3. `age -d -i <приватный ключ> -o /tmp/restore.dump /tmp/restore.dump.age`
4. `docker run --rm -d --name shk-restore-test postgres:15-alpine` + `pg_restore` в пустую базу
5. контрольный запрос (`select count(*) from users`) и снос контейнера

Если локальный Docker недоступен — резервный путь: тот же прогон на VPS, приватный ключ подаётся
через process substitution и на диск VPS не пишется. Резервный путь помечается в отчёте явно,
потому что он слабее по инварианту 8.

## Не делаем

- Не переносим Foodzy на новый механизм и не правим его скрипт.
- Не трогаем firewall, сеть, схему БД.
- Не строим мониторинг: дашборды, метрики, healthchecks-сервис — отдельная задача.
  Telegram-уведомление о провале мониторингом не считается (уточнение оркестратора).
- Не меняем существующий `shkoder-pg-backup.sh`, его cron и его локальный retention.
- Не трогаем `ops/compose/deploy.py`.
- Не бэкапим redis Harry и кэши `harry-hermes-data`.
